# 4단계 토론 프로토콜 변형

`SKILL.md` 4단계(근거 기반 패널 토론)의 **토론 구조 4라운드**를 안건 성격에 맞는 것으로 교체한다. `--protocol [premortem|redblue|board|delphi]`로 지정하거나, 0단계 판정에서 해당 상황이면 한 문장으로 제안한 뒤 쓴다.

**어떤 프로토콜을 쓰든 유지되는 것**: 근거 수준 태그(Hard Rules #1), 원문 URL 원칙(#5), 시뮬레이션 고지(#7), Gate 4 출력. 프로토콜은 토론의 *구조*를 바꾸지 *근거의 기준*을 낮추지 않는다. 프로토콜을 썼으면 Gate 4 줄에 어떤 프로토콜인지 함께 적는다.

---

## 1. 프리모템 (`--protocol premortem`) — 되돌릴 수 없는 결정

**언제**: 0단계 가역성 판정이 "불가" 또는 "어려움". 계약 서명, 법인 등기, 상근 전환, 큰 금액 집행.

기존 4라운드를 이렇게 교체한다:

1. **실패 고정**: "2028년 __월. 이 결정은 명백히 실패했다"를 전제로 놓는다. 성공 가능성은 이 라운드에서 논의 금지.
2. **원인 분기**: 각 전문가가 **서로 다른 실패 원인**을 하나씩 쓴다. 중복이 나오면 뒤에 쓴 사람이 다시 쓴다. 원인에도 근거 태그를 단다 — 2단계 근거 지형에서 이 실패 유형이 얼마나 흔한지 확인된 것과 추측을 구분하기 위함이다.
3. **징후 역추적**: 각 원인에 대해 — 최초 징후는 무엇이었나 / 언제 알 수 있었나 / 그때 무엇을 했어야 하나.
4. **교차 검증**: 원인들 중 실제로 통제 가능한 것만 남긴다.

**산출물 연결**: 3번의 "최초 징후"를 6단계 킬 크라이테리아로 그대로 옮긴다. 이것이 프리모템의 진짜 산출물이다.

가장 흔한 실패: 원인을 "운이 나빴다", "시장이 안 좋았다"로 쓰는 것. 통제 불가능한 원인은 4라운드에서 잘라낸다.

## 2. 레드팀 vs 블루팀 (`--protocol redblue`) — 이미 마음이 기운 안건

**언제**: 0단계 Mirror에서 키키가 사실상 결정했고 확인만 받고 싶어 하는 게 감지될 때. B형 특성상 자주 발생 — 감지되면 먼저 제안하라.

1. **블루팀 3인**: 이 결정을 **최선의 형태로** 실행하는 계획을 만든다 (근거 지형의 처방적 발견을 최대한 활용).
2. **레드팀 3인**: 그 계획만 공격한다. 결정 자체가 아니라 **계획의 가장 약한 고리**를 노린다.
3. **응답 라운드**: 블루팀이 각 공격에 "수정 / 감수 / 반박" 셋 중 하나로 답한다. `[Contested]` 근거를 근거로 든 공격은 반박이 아니라 반드시 "감수"로 처리한다.
4. **결론**: 결정을 바꾸지 않되 **계획이 달라진 지점**을 명시한다. "감수"를 고른 항목이 곧 리스크 목록이고, 6단계 관찰 포인트가 된다.

## 3. 이사회 시뮬레이션 (`--protocol board`) — 이해관계자가 여럿인 안건

**언제**: 오로라플래닛 지분·역할·투입량처럼 다른 사람의 이해가 직접 걸린 안건.

1. **이해 지도**: 각 이해관계자의 **이익·불안·레드라인**을 표로 먼저 쓴다 (발언 이전에).
2. **재서술**: 같은 사실을 각자의 관점에서 다시 쓴다 — 무엇이 다르게 읽히는가.
3. **ZOPA 분리**: 합의 가능 영역과 진짜 충돌 지점을 나눈다.
4. **확인 표시 (필수)**: 각 관점 옆에 "이건 추정이다 / 이 사람에게 직접 물어야 한다"를 표시한다.

⚠️ 이 프로토콜은 로스터 C를 여러 명 세우는 구조라 실명 오귀속 위험이 가장 크다. 4단계 민감 주제 가드를 반드시 적용하고, 각 발언에 `(시뮬레이션)`을 병기한다. 주식회사 키키 정관 제5조 결재 라인상 이 시뮬레이션은 CEO-aurora 검토 **전** 단계일 뿐이다 — 여기서 나온 결론으로 상대와의 합의를 대체하지 않는다.

## 4. 델파이 수렴 (`--protocol delphi`) — 쟁점이 너무 많을 때

**언제**: 교차 검증 후에도 쟁점이 5개 이상 남아 산출물이 무거워질 때.

1. 각 전문가가 **비공개로** 1~10 점수를 매긴다 (10 = 반드시 실행).
2. 점수 분포와 **극단값의 이유만** 공개한다 (평균은 무시 — 평균은 아무의 의견도 아니다).
3. 극단값의 이유를 읽은 뒤 재채점한다.
4. 2회차에도 좁혀지지 않으면 그 항목은 **정보 부족**으로 확정하고 6단계 "확인할 사실"로 보낸다. 더 논의하지 않는다.

## 5. 강제 반대자 — 근거 약한 만장일치 (플래그 없음, 자동 발동)

1라운드에서 전원 같은 방향인데 근거가 `[Emerging]`/`[Expert]`/`[Internal Knowledge]` 위주면 자동 발동한다:

1. 가장 강하게 찬성한 전문가에게 **반대 논거만** 다시 쓰게 한다.
2. 그래도 반대가 안 서면 로스터 D에서 레드팀 1인을 추가 캐스팅한다.
3. 그래도 안 서면 산출물에 "이 안건은 실질적 쟁점이 없다 — 만장일치의 근거는 `[__]` 수준"이라고 쓰고 짧게 닫는다. **억지 쟁점을 만들지 않는다.**

근거가 `[Strong]`으로 수렴한 만장일치에는 발동하지 않는다. 강한 근거 앞의 합의는 문제가 아니다.

## 프로토콜 선택표

| 상황 | 프로토콜 |
|---|---|
| 되돌릴 수 없다 | 1. 프리모템 |
| 이미 결정했다 | 2. 레드팀 vs 블루팀 |
| 남의 이해가 걸렸다 | 3. 이사회 시뮬레이션 |
| 쟁점이 너무 많다 | 4. 델파이 수렴 |
| 근거 약한 만장일치 | 5. 강제 반대자 (자동) |
| 오늘 결정해야 한다 | 프로토콜이 아니라 `--quick` (1-2단계 생략) |
| 위 어디에도 안 맞는다 | `SKILL.md` 4단계 기본 4라운드 |

`--quick`과 프로토콜은 함께 쓸 수 있다 (예: `--quick --protocol premortem`). 다만 `--quick`은 근거 지형을 건너뛰므로 새로 인용하는 근거에 `[Internal Knowledge]` 태그와 한계 고지가 붙는다 — 되돌릴 수 없는 결정에 이 조합을 쓰는 건 권하지 않는다. 그런 결정에서 아낀 30분은 나중에 몇 달로 돌아온다.
